## 4. تصميم انتقال التسجيل اللاحق — ليس منفذًا هنا

إعادة استخدام سجل `f01a_defensive_ingress` والحارس القائم؛ لا برنامج أو runtime أو socket جديد.

بعد مراجعة هذا التصميم وقرار المالك المحدد، يكون فرق السجل اللاحق محصورًا في:

1. إضافة المسار الواحد إلى allowed_paths، دون إعادة كتابة scope_document أو owner_scope_decision أو registration_decision أو subject أو start_decision التاريخية.
2. إضافة حدث واحد مقترح باسم `SCOPE_EXTENSION` إلى نهاية events، بعد STOP، مع حفظ الحدثين السابقين كاملين وبترتيبهما. الاسم وعقد الحدث مقترحان للتحقق الحاكم فقط، وليسا معرف runtime أو API.
3. يحدد الحدث قائمة حقول مغلقة: type، recorded_at، baseline_commit_sha، added_paths، scope_addendum، owner_scope_decision، effect. يكون effect=`SCOPE_EXTENSION_ONLY_NO_RESUME` وadded_paths القائمة ذات العنصر الواحد. scope_addendum يحمل URL/commit/blob المثبتة للملحق؛ owner_scope_decision يحمل ID ورابط القرار وتوقيته وموضوعه وأثره، مثبتة في حارس مراجع مستقل عن بيانات السجل.
4. موضوع القرار والتسجيل رأس موجود محقق عند إعداد الانتقال؛ لا SHA مفترض لcommit يحتوي نفسه، ولا مرجع main متحرك. يربط القرار بالمقترح المراجع وcheckpoint وملحق النطاق. عند اختلاف المرجع عن الرأس أعلاه يُفحص الفرق قبل استخدام الأدلة؛ لا تُنقل موافقة رأس قديم.
5. تبقى الحالة IN_PROGRESS والتنفيذ false، وdelivery_evidence=null، وclosure_effect=NONE، والبيئة DARK_OFFLINE. يبقى active_target نفسه وحد التنفيذ الواحد، وكل أعلام الشبكة/المزود/النشر false.
6. ينشئ الحارس المتوقع من STOP المثبت + الزيادة المعتمدة المحددة، لا من السجل الذي يفحصه. تبقى oracles التاريخية واختبار lifecycle المعزول كما هي؛ لا توسيع fixture لإجازة المصدر الحقيقي أو قبول START بدل STOP.
7. حد الاستئناف محفوظ: **NEW_OWNER_DECISION_AND_REVIEWED_EXACT_HEAD_GOVERNANCE_TRANSITION**. بعد نفاذ التسجيل يبقى الإصلاح متوقفًا، حتى قرار استئناف جديد على checkpoint ورأس محقق وانتقاله المراجع؛ لا إعادة تشغيل من وجود المسار أو نجاح CI.

هذا تصميم تسجيل مقترح؛ لا إضافة لحقول أو أحداث أو صلاحيات في المصدر النافذ الآن. سجل التنفيذ يبقى مصدر الحقيقة الوحيد، وليس أسماء الحالات داخل الوثائق.
