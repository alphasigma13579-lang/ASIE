# F-01A — مقترح نطاق فهرس إثبات المنشأ فقط

الحالة: **PROPOSED / REVIEW_REQUIRED / NOT_EFFECTIVE / NOT_IMPLEMENTED**.
التاريخ: 2026-10-11. هذا تصميم محصور للإعداد والمراجعة، لا تسجيل نافذ ولا استئناف أو كود SQLite أو دمج أو تشغيل على قاعدة المالك.

- التطبيق منفصل في [Draft #189](https://github.com/alphasigma13579-lang/ASIE/pull/189)، رأس checkpoint: `7df4ea3c6dfbcfb70cc219ef59622b7387052dc4`؛ tree: `1f09e998db26e46223c4e9287636487004f0bffa`.

السجل النافذ ما زال F01A `IN_PROGRESS/true`، تسعة مسارات مرتبة، وسبعة أحداث تنتهي بـRESUME. التوقف العملي عن تعديل التطبيق أثناء إعداد هذا المقترح ليس STOP حاكمًا نافذًا؛ لا نزعم أن manifest أصبح false قبل انتقال مستقل مصرح ومراجع.

## 2. لماذا يحتاج قرار نطاق

[الخطة الأصلية §4](FC20-12-F01-TRUSTED-CONTEXT-INGRESS-REPAIR-PLAN-2026-10-01.md) و[إلحاق الاستهلاك §7](FC20-12-F01A-APPROVAL-CONSUMPTION-SCOPE-ADDENDUM-2026-10-09.md) يمنعان SQLite schema صراحةً. `backend/repository.py` و`tests/test_repository_intelligence.py` موجودان أصلًا ضمن المسارات التسعة؛ الاستثناء المطلوب للعملية، لا إضافة مسار عاشر صوري.

موافقة المالك بتاريخ 2026-10-11 11:49:57 UTC تسمح ببدء إجراء إعداد التوسعة المحكوم للفهرس واختبارات التوافق والتراجع فقط. لا تحل محل قرار قبول التصميم المحدد أو إعداد التسجيل أو دمجه أو الاستئناف أو تنفيذ الفهرس. لا نسجل رابط قرار حاكم غير موجود؛ يثبت مرجع القرار الفعلي ورأس التصميم وblob عند المرحلة المصرح بها.

## 3. الاستثناء المقترح المغلق

فهرس واحد غير فريد، داخل `Repository.init_schema()` القائم:

```sql
CREATE INDEX IF NOT EXISTS idx_security_audit_origin_proof
    ON security_audit_events(action, target_type, target_id, organization_id);
```

الأعمدة وترتيبها والجدول والاسم والنوع غير الفريد مثبتة لهذا المقترح. لا جدول أو عمود جديد، لا تعديل صفوف أو backfill لدليل منشأ، لا إعادة ترميز proof أو تغيير شروط استعلامه أو عدد الأدلة المقبول أو معاملته الذرية. تبقى قاعدة رفض السجل القديم غير المثبت عند replay كما هي، وتبقى القراءة التاريخية المسموح بها منفصلة.

إذا وجد فهرس بالاسم نفسه وتعريف مختلف، لا يسقطه التنفيذ تلقائيًا ولا يصلحه بصمت: يرفض التعارض ويطلب قرارًا. قد تفشل التهيئة عند هذا التعارض؛ قبول هذا السلوك التوافقي جزء من قرار التصميم اللاحق، وليس تغييرًا منفذًا. إنشاء الفهرس قد يكلف وقتًا ومساحة وقفلًا عند تهيئة قاعدة قائمة؛ لا تفويض لتشغيل ذلك على قاعدة فعلية من هذا المقترح.

التطبيق اللاحق، إن فوض بعد بواباته، محصور في:

1. `backend/repository.py`: إنشاء الفهرس المحدد والتحقق من توافق تعريفه عند التهيئة، دون تغيير استعلام الدليل أو مصدره.
2. `tests/test_repository_intelligence.py`: أدلة معزولة للفهرس والتوافق والتراجع ودلالات replay.

لا تعديل schema أو test أو أي ملف تطبيق في مرشح التصميم الحالي. ملفا المرشح فقط هذه الوثيقة و`docs/EKB/README-AR.md` كرابط ملاحي. لا تعديل الوثائق المرجعية المثبتة أو حراسها لإقرار تصميم قبل مراجعته.

## 4. تمثيل التسجيل المقترح — يحتاج مراجعة مستقلة

هذا التمثيل اقتراح جديد لعملية واحدة؛ ليس حقلًا مفترضًا أنه موجود في عقد التسجيل الحالي.

يقترح انتقال STOP_CHECKPOINT ثم SCOPE_EXTENSION، بإبقاء `allowed_paths` التسعة دون تغيير، وتثبيت استثناء schema واحد بهوية:

```json
{
  "operation": "CREATE_INDEX_IF_NOT_EXISTS",
  "index_name": "idx_security_audit_origin_proof",
  "table": "security_audit_events",
  "columns": ["action", "target_type", "target_id", "organization_id"],
  "unique": false,
  "implementation_path": "backend/repository.py",
  "test_path": "tests/test_repository_intelligence.py"
}
```

يقترح الحقل `allowed_schema_operations` في شريحة F01A بهذه القائمة الوحيدة، و`added_schema_operations` المطابق في حدث SCOPE_EXTENSION، مع `added_paths: []`. يثبت الحدث مرجع التصميم المراجع وقرار المالك الفعلي ورأس التطبيق والـbaseline. يجب أن يطابق موضوع قرار RESUME اللاحق هذا الاستثناء نفسه، لا المسارات وحدها. اختيار أسماء الحقول هذا غير نافذ حتى قبول التصميم وتثبيت oracle مستقل؛ لا يستنتج تفويض من metadata أو قيمة truthy أو حقل غير معروف.

حارس التسجيل اللاحق يجب أن يرفض: فهرسًا ثانيًا، اسمًا/جدولًا/ترتيب أعمدة مختلفًا، unique=true، إزالة أحداث، زيادة مسار، تشغيلًا ضمنيًا أو RESUME قديمًا. يعكس الانتقال كاملًا إلى manifest blob المرجعي، ويحفظ سلسلة oracles السابقة وprefixes الإسقاطات الخمسة وأختامها الخاصة. يفحص oracle التصريح الحاكم، أما عدم تغيير SQL/proof الفعلي فيثبت بفحص فرق التطبيق واختبارات القبول، لا بحارس manifest وحده. العكس يزيل الحقل الجديد والحدثين ويعيد execution_authorized=true حرفيًا لإنتاج blob المرجعي قبل اختبار سلسلة CRG→CS→RG→SG القائمة.

## 6. قبول التنفيذ اللاحق والتراجع

**الفهرس NOT_IMPLEMENTED؛ اختبارات الفهرس TESTS_NOT_RUN.** المطلوب بعد التفويض:

- تحقق metadata للـschema مع `PRAGMA index_list/index_info/index_xinfo` من الجدول والاسم والأعمدة وترتيبها وعدم uniqueness، مع اتجاه ASC وcollation BINARY الافتراضيين، وعدم وجود WHERE جزئي أو تعبير بديل. يرفض الاسم نفسه على جدول آخر أو أي تعريف مختلف؛ `IF NOT EXISTS` وحده لا يثبت توافق التعريف. قاعدة جديدة وقاعدة اختبار قديمة، وتهيئة متكررة بلا تكرار أو تغيير سجلات؛ تعارض تعريف موجود يرفض بلا إسقاط.
- `EXPLAIN QUERY PLAN` يستخدم SEARCH بالفهرس المحدد بدل SCAN للاستعلام نفسه. لا ادعاء covering index للصف كله؛ الاستعلام SELECT * وقد يحتاج قراءة الصف بعد تضييق النتائج.
- تبقى مجموعة نتائج الدليل وعددها وتعدد الأدلة ورفض التزوير وtenant/project isolation وreplay الصحيح وCAS ومعاملة record+proof/rollback كما هي؛ لا backfill أو تغيير JSON.
- قياس اصطناعي معزول قبل/بعد على أحجام مثبتة، مع تسجيل بيئة/طريقة القياس وكلفة إنشاء الفهرس وحجم الملف. لا threshold زمني هش أو استنتاج زمن قاعدة المالك. فحص تنازع كاتب معزول لا يزيل BEGIN IMMEDIATE أو يضعف الذرية.
- تراجع معزول: عكس الكود يوقف إنشاء الفهرس والتحقق الجديد في التهيئات اللاحقة، لكنه لا يزيل الفهرس الموجود ولا يعطله؛ قد يظل SQLite يستخدمه تلقائيًا. إزالة الفهرس عملية منفصلة تحتاج إذنًا. اختبار إسقاط الفهرس المحدد وإعادته داخل قاعدة اختبار مؤقتة فقط يثبت بقاء الصفوف والدلالات. إسقاطه من قاعدة المالك غير مفوض.
- الاختبارات المركزة ثم exact-head CI المطلوب ومراجعة مستقلة. لا إعادة full suite ناجح دون delta، ولا نقل أدلة رأس سابق، ولا إغلاق ملاحظة المراجعة قبل الدليل والتفويض.

حد التوقف: غياب قبول التصميم أو القرار المحدد أو نفاذ التسجيل/RESUME، اختلاف baseline، أو الحاجة إلى أي schema operation أخرى يوقف الجزء المتأثر ويعرض القرار، لا يتوسع التنفيذ تلقائيًا.
