## النطاق
محول جديد مستقل خارج المسار الجاري: SQLite WAL/FULL، قفل مضيف بين العمليات، scope موثوق قبل I/O، revision، سجل نية وخطوات، هوية إعادة محاولة محفوظة، وامتناع عند عملية غير نهائية. لا عميل مزود أو route جديد.
## القبول
- اختبارات عمليات مستقلة للكتابة المتزامنة وموت الكاتب وإعادة فتح السجل.
- رفض tenant/preflight/forged scope قبل إنشاء الملفات، رفض المسارات المرتبطة، schema غير مدعوم، إعدادات متانة مخالفة، وتعارض revision/نية/epoch.
- تثبيت النية والخطوات قبل commit وتثبيت corpus والنتيجة النهائية في معاملة واحدة؛ rollback على الخطأ؛ الرسائل رموز ثابتة بلا استثناء خام.
- نجاح اختبارات Linux وWindows الجديدة والفحوص القائمة ومراجعات الرأس النهائي؛ TestSprite غير المفعّل مستثنى.

## إضافة معتمدة — حماية نظام الملفات وكلفة الفحص
وافق المالك على معالجة ملاحظات #165 الخاصة بسباق تبديل المسارات وكلفة فحص القاعدة عند كل جلسة.
الخطة: تثبيت حدود مجلد خدمة خاص ثم فتح الملفات دون اتباع الروابط، وإبقاء مقابض Windows لملف القفل والقاعدة وWAL/SHM بدون مشاركة الحذف حتى يغلق SQLite. سجل rollback المؤقت وحده يسمح بمشاركة الحذف كي تتمكن SQLite من إنهائه أثناء التهيئة، داخل المجلد الخاص المتحقق من صلاحياته. يتحقق Linux من ملكية المجلد وصلاحياته ويستخدم openat/O_NOFOLLOW؛ يتحقق Windows من owner/DACL عبر مقابض فعلية ويرفض reparse points وقرص الشبكة. لا يصلح التطبيق الصلاحيات تلقائيًا.
المجلد يجهزه المشغل مسبقًا، بلا صلاحيات وصول لحسابات غير موثوقة؛ حساب الخدمة ومدير نظام المضيف ضمن حد الثقة. لا ندعي العزل من عملية مخترقة تحمل هوية الخدمة نفسها أو من root/Administrator. هؤلاء يستطيعون أصلًا تعديل ذاكرة العملية/قاعدة البيانات؛ يلزم عزل هوية الخدمة تشغيليًا قبل أي نشر.
تشمل الحماية ملفات lock وdatabase وWAL وSHM وrollback journal، ولا تُغيّر ملفات أخرى. في Windows قد تبقى الملفات الجانبية بعد close لأن مقابض الحراسة تمنع حذفها؛ تديرها SQLite عند إعادة الفتح، ولا يحذفها المحول يدويًا.
الفحص الروتيني يتحقق من schema والسجل الأساسي وcorpus محدود الحجم، ولا يمس تاريخ العمليات كاملًا. الاستعلام عن عملية معلقة يستخدم الفهرس الجزئي (عنصر واحد كحد أقصى). الفحص الشامل ينتقل إلى verify_integrity() صريح داخل جلسة المنصة وبالقفل نفسه؛ يجب أن تستدعيه شرائح النسخ والاستعادة اللاحقة. لا واجهة جديدة ولا جدولة تشغيل تلقائية.
اختبارات الإضافة: تبديل المسار قبل الفتح مع منع SQLite وعدم تغيير الهدف، ACL/mode غير آمن، تثبيت أسماء الملفات على Windows، استمرار اختبارات التزامن والانقطاع، وإثبات عدم تشغيل scans كاملة عند كل session مع بقاء فحص الصيانة صريحًا.
مصادر أولية: [Python descriptor-relative open](https://docs.python.org/3/library/os.html#os.open)، [Win32 no-follow and sharing](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)، [handle security descriptor](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-getsecurityinfo).
التقدير الإضافي 15–30 ألف توكن للقياس فقط. بوابات القبول ونقطة التوقف السابقة ثابتة؛ لا دمج ولا نشر.

نتيجة التشخيص: Windows رفض fixture ذي ACL زائد كما هو مطلوب؛ جرى إنشاء ACL مطابق داخل مجلد pytest فقط. ثم أثبت الاختبار ضرورة السماح لـSQLite بحذف rollback journal أثناء التهيئة. لا إعدادات نظام أو بيانات مالك عُدّلت. يختبر حارس الملفات ذاته مباشرةً بالإضافة إلى اختبارات المحول.
