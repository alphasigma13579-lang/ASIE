## 3. النموذج الأدنى المقترح: أهلية ثم إذن ثم نتيجة

هذه أسماء **حالات مقترحة لسجل الشريحة اللاحق**، لا حالات متاحة في v1 الآن ولا تغيير لحالات الحزم:

| الحالة المقترحة | شرطها / أثرها | ما لا تسمح به |
|---|---|---|
| REGISTERED_BLOCKED | الافتراضية؛ الدليل أو السلطة ناقصان، أو تغير النطاق / أبطل دليل | بدء كود الشريحة، ملء slot أو تشغيل خارجي |
| ENTRY_VERIFIED | مخطط وحارس معتمدان ومطبقان، الضوابط التسعة مستوفاة فعليًا للنطاق، ومراجعة الدخول على المرشح | لا بدء تلقائي؛ slot تبقى فارغة دون قرار بدء مستقل |
| IN_PROGRESS | قرار بدء مالك صالح للنطاق الداكن، وخطة ملفات/أوامر معتمدة، وslot واحدة مطابقة؛ تحقق الدخول ما زال صالحًا | لا اعتماديات أب أو شبكة/مزودات/SDK أو نشر أو بيانات مالك |
| DARK_DELIVERY_VERIFIED | دليل تنفيذ وفحوص ومراجعات وتراجع مطابق للمرشح ثم قبول نتيجة الشريحة | لا COMPLETE للأب أو 08/09/11/05، ولا تشغيل حي أو دعوات |

لا ترقية بسبب الزمن أو CI أخضر أو تعطل المراجع. يمكن جمع قبول الدخول وقرار البدء في سجل قرار واحد فقط إذا فصل أثرهما صراحةً وطابق كل شروطهما؛ لا يُفترض ذلك من «اعتمد» دون نطاق معلوم.

عند تغير شرط أثناء التنفيذ: يمنع الاستمرار أو بدء أثر جديد ضمن الشريحة المتأثرة، وتسجل واقعة الحجب مع بقاء ادعاء النشاط محسوبًا حتى توثيق التوقف وإفراغ slot بقرار محكوم. **لا تُمحى IN_PROGRESS لمجرد تغييرها إلى BLOCKED لإخفاء تنفيذ ثانٍ.** لا يدعي حارس المستودع إيقاف process أو إلغاء طلب سبق إرساله؛ حدود الأثر الفعلية تبقى في التطبيق.

مخططا registration.v1 وexecution-sequence.v1 الحاليان يبقيان صالحين للتسجيل المحجوب التاريخي فقط. التطبيق المستقبلي يعرّف نسخة دليلية صريحة وتوافقها واختباراتها؛ لا يوسع v1 بصمت ولا يزيل assertions دون بديل يحفظ invariant نفسه. حالات FC20-01..16 وأدلة COMPLETE وعددها واعتمادياتها لا تستبدل بحالات الشريحة.

## 4. البيانات المقترحة للأهلية — ليست schema مسجلة

يضاف التمثيل، عند اعتماده، داخل سجل FC20-12 نفسه مع execution_sequence القائم؛ لا مخزن موازٍ أو API تفويض جديد.

| المجموعة | الحد الأدنى المقترح |
|---|---|
| الهوية والنطاق | program/package/slice IDs الثابتة، نسخة المخطط، رابط/commit/blob النطاق المعتمد، نسخة المقترح وقرارها؛ قائمة الأوامر والملفات المحددة |
| موضوع الدليل | subject commit وtree، مسارات/blobs المتأثرة والعقود/إصداراتها، نطاق البيئة OFFLINE/DARK، أنواع الأثر المسموحة والممنوعة |
| لكل ضابط من التسعة | المالك الحالي نفسه، حالة إثبات، evidence refs غير فارغة عند التحقق، نوع الادعاء، طريقة/نتيجة التحقق، الوقت، حدود التطبيق، أسباب عدم إعادة الاختبار إن أعيد استخدام دليل |
| الإثبات التنفيذي حيث يلزم | أسماء/مسارات الاختبارات ونتائجها الفعلية، workflow/check/run IDs ورأسها، artifact مرجعه وبصمته القابلة للتحقق؛ لا URL أو رقم run وحده كدليل نجاح |
| القرارات والمراجعات | صاحب القرار ووقت UTC والنطاق والسبب والشروط، مرجع النسخة/الرأس، مراجع نتائج البرنامج/AAS/الأمن/AI؛ مستقلًا عن رأي المؤلف الذاتي |
| البدء والنشاط | قرار بدء منفصل، حدود خطة الكود الداكن، target مطابق للخانة، max_active_executions = 1، checkpoint/hold وشرط الاستئناف؛ أي حجب أو إبطال لاحق محفوظ |
| التسليم | مرشح التنفيذ النهائي، نتائج فحوص §10 والتراجع والتوافق والمخاطر، قرار قبول النتيجة؛ ليس أثر إغلاق الأب |
| أثر السلطة | parent closure = NONE؛ network/provider/deployment/public release/invitations غير مأذونة بهذا الانتقال |

أنواع دليل الضابط المقترحة تميز PENDING وVERIFIED وREJECTED؛ لا N/A لتجاوز أحد الضوابط التسعة. إن احتاج التصميم تغيير معنى ضابط أو مالكه، فهو تعديل نطاق مستقل لا «توافق مخطط». رفض الحقول/الحالات/الملاك/الأوامر غير المعروفة أو المكررة واجب، وكذلك الأنواع الخاطئة وغياب المراجع.

execution_authorized، إن أبقي لعرض التوافق، نتيجة تحقق من السجل والقرارات لا مدخل مستقل يفتح التنفيذ. سجل CI حارس اتساق، **ليس** تصريح runtime أو توقيعًا مشفرًا أو إثباتًا لهوية صاحب القرار. قرار المالك يثبت في سياقه الموثق ويراجع بشريًا؛ لا يُستنتج من اسم البريد أو asie أو حقل reviewer.

## 5. ربط الرأس والدليل دون دورة SHA ذاتية

1. الدليل السابق يثبت **موضوعًا محددًا موجودًا**: commit/tree/blobs ونطاق واختبارات وعقود. لا يطلب من ملف الإشارة إلى SHA نفسه قبل إنشاء commit، ولا تختلق workflow أو hashes لكود لم يبن.
2. PR الحارس اللاحق يراجع على رأسه النهائي؛ مراجعاته ونتائج CI تثبت خارج commit في سجل PR. إذا أريد تثبيتها في Git، يكون ذلك في أثر تالٍ يشير للرأس المفحوص، لا إعادة كتابة نتيجة مستقبلية داخل الرأس الأصلي.
3. استخدام دليل رأس أقدم يتطلب مطابقة الفرق وblobs التي يغطيها، وتعليل الثبات ومراجعة نطاقه. **لا تنتقل موافقة الرأس القديم آليًا**؛ الرأس الحالي له مراجعاته وفحوصه اللازمة، وإعادة الاختبار فقط عند تغير مؤثر أو تناقض أو فشل متقلب موثق.
4. مرجع GitHub إلى main متحرك ليس تثبيتًا. أدلة الملفات تثبت commit/blob؛ نتائج PR/review/workflow تطابق الرأس الفعلي والمحتوى عند التحقق، مع أثر منقح مثبت إذا كان المصدر قابلًا للتحرير.
5. الحارس يتحقق من الأدلة المتاحة فعلًا وقابلة للمطابقة ضمن CI المحكوم؛ لا ينشئ fetch خارجيًا أو يفترض أن صيغة SHA/URL تثبت صحة المضمون. تحقق الهوية/القرار والمراجعة مستقل عن تطابق بنية السجل.
6. تغيير نطاق الأمر أو العقد أو الضابط، إبطال المصدر/القرار، تعارض الرأس، دليل فاشل أو غير قابل للتحقق، أو انقضاء مدة مقررّة في القرار يمنع استعمال الأهلية المتأثرة. لا توجد مدة افتراضية مخترعة؛ مدة صلاحية القرار إن وجدت يحددها المالك. انتهاء مراجعة آلية بالحصة أو skip ليس نجاحًا.
