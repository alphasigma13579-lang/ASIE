# F05-01 — تصميم التخزين المعاملاتي للمعرفة الاقتصادية العامة

التاريخ: 2026-09-09. الحالة: **تصميم مقترح للتنفيذ المعزول، وليس تنفيذًا أو تصريح تشغيل حي**.

- السلطة: [ACR FC20-05](ACR-FC20-05-PUBLIC-ECONOMIC-KNOWLEDGE-2026-08-23.md) و[نطاق المعرفة العامة](EKB/domains/Public-Economic-Knowledge.md)؛ لا تستبدل هذه الوثيقة سلطتهما.

## القرار والبدائل

الاختيار: محول مستقل باستخدام SQLite المدمج، وقاعدة خاصة بالمعرفة العامة، مع **قفل عملية محلي واحد وسجل عمليات دائم**. معاملات قاعدة البيانات قصيرة؛ لا تبقى معاملة SQLite مفتوحة أثناء طلب الشبكة.

البدائل:

1. JSON مع قفل: قد يمنع فقد الكتابة، لكنه يحتاج أيضًا journal ومعاملات متعددة وسلامة استيراد؛ لا يحل فجوة الانقطاع وحده.
2. SQLite مع revision فقط: يمنع فقد الحفظ محليًا لكنه لا يمنع كاتبين من إرسال آثار متعارضة للفهرس قبل فشل أحد الحفظين.
3. خدمة قاعدة بيانات/صف رسائل جديد: لا حاجة مثبتة إليه لهذه الشريحة؛ يزيد التشغيل دون إزالة ضرورة التعافي من آثار المزود.

إعداد المتانة المقترح: SQLite journal_mode=WAL وsynchronous=FULL وforeign_keys=ON. يتحقق المحول من القيم الفعلية على اتصالاته قبل قبول أي كتابة؛ اختلافها أو عدم دعمها فشل مغلق، ولا تخفيض تلقائي إلى NORMAL/OFF. commit سجل النية يجب أن ينجح قبل الأثر الخارجي. ملفات WAL وSHM جزء من حالة التشغيل ولا تُحذف أو تُنسخ منفردة؛ النسخ حصريًا عبر backup API. يفترض هذا الضمان تخزينًا محليًا يحترم flush/fsync؛ الإعداد وحده لا يثبت متانة المضيف.

حد الدعم المقترح: **مضيف واحد وتخزين محلي دائم واحد، وكل الكاتبين يستخدمون المحول نفسه**. ليس ضمانًا متعدد المضيفين أو فوق NFS. إذا تطلب النشر غير ذلك، تتوقف الشريحة التشغيلية ويعاد قرار التزامن؛ لا يُفترض دعمها.

## المخزن والملكية

اسم مقترح: `public_knowledge.sqlite3` في مسار خادمي معتمد داخل تخزين التطبيق الدائم. لا يقبل مسارًا أو namespace من المتصفح.

أقل مخطط مقترح، version مستقل عن نسخة corpus:

- `corpus_state`: صف واحد، revision متزايد، restore_epoch، وJSON corpus المتحقق منه. إصدار مخطط المخزن في PRAGMA user_version، وليس عمودًا في الجدول؛ schema_version داخل JSON يخص عقد corpus. إبقاء شكل corpus الأصلي يقلل تغيير عقود المستهلكين، ولا يعني إبقاء الحفظ JSON خارجيًا.
- `operations`: operation_id فريد للتتبع، workload موثوق، restore_epoch، idempotency_key_hash، intent_digest، النوع، revision الأساسي، الحالة، before/after images المتحقق منها، قوائم IDs التي قد تتأثر، نتيجة نهائية آمنة محفوظة، وتواريخ. قيد UNIQUE(restore_epoch, workload, idempotency_key_hash) يثبت هوية الاستئناف بعد إعادة تشغيل العملية؛ يحسب digest من تمثيل canonical محدد للنية. البحث بهذا القيد ومقارنة digest يتمان ذريًا قبل إنشاء عملية جديدة؛ لا تخزين للمفتاح الخام في سجل تشخيصي، ولا تقليم لربط الهوية قبل سياسة احتفاظ معتمدة. البيانات اللازمة للتعافي تُحفظ **قبل** أي أثر خارجي.
- `operation_steps`: ترتيب المصدر/الدفعة، نية الأثر، تقدم التنفيذ/التعويض، دون نص استثناء أو سر.
- `imports`: بصمة الملف وإصدار الاستيراد وإجمالي السجلات للتحقق من التكرار.
- القيود: schema معروف فقط؛ revision المقارن مطلوب في commit؛ عملية غير نهائية واحدة لكل corpus؛ تفعيل قيد المفاتيح الأجنبية والتحقق من schema والسجل الأساسي عند فتح الجلسة. فحص integrity_check وforeign_key_check الشامل صيانة صريحة تحت القفل، وإلزامي عند النسخ والاستعادة، وليس مسحًا لتاريخ العمليات في كل اتصال. رفض schema أحدث بدل تخفيضه صامتًا. هذه مواءمة مع محول F05-01A المدموج في #165؛ لا تغيّر بوابات التعافي أو التشغيل.

يبقى سجل التدقيق ودورة المصدر والنسخ المحدودة داخل corpus متوافقين. السجل التشغيلي لا يحذف عملية غير محسومة، ولا يُختزل إلى آخر N نسخ قبل إغلاق التعافي. سياسة تقليم السجل والنسخ الاحتياطية تحتاج قرار احتفاظ؛ لا حذف تلقائي جديد في هذه الشريحة.

الكتابة/الحذف/الاستعادة/إعادة البناء تخص عبء المنصة المعتمد `public-knowledge-sync` فقط. تحقق النطاق يسبق فتح مخزن للكتابة أو إنشاء عميل مزود. قراءات المستأجرين تمر عبر التفويض الحالي ولا تستطيع إدارة corpus أو journal؛ الملفات نفسها ليست واجهة عميل.

## التزامن والتعافي

### القفل

- قفل نظام تشغيل حصري يغطي دورة العملية كاملة، بما فيها طلبات المزود والتعويض. يُستخدم قفل متوافق مع Linux/Windows خلف محول صغير، وتثبت دلالاته باختبارات عمليات منفصلة قبل ربطه.
- ملف قفل ثابت في مجلد خاص بالخدمة؛ لا يحذف بعد فك القفل حتى لا تنشأ أقفال على ملفات مختلفة. توحيد المسار ورفض الروابط/الأسماء البديلة غير المعتمدة؛ صلاحيات المجلد تمنع الاستبدال من طرف غير مخول.
- يشترك run وdelete وrestore وreindex وrecovery وimport وbackup وrestore-backup في القفل نفسه. يتأكد المحول من ملكيته قبل تعديل corpus أو journal.
- انتظار محدود ثم حالة تشغيلية آمنة «عملية معرفة أخرى قيد التنفيذ؛ أعد المحاولة لاحقًا». لا سرقة قفل بناء على عمر lease أو PID فقط، ولا حلقة إعادة محاولة غير محدودة.
- تحرير القفل بعد موت العملية لا يثبت انتهاء طلب سبق إرساله إلى المزود. **انظر بوابة الآثار المتأخرة أدناه**؛ لا يبدأ كاتب جديد تلقائيًا لمجرد توفر القفل.
- الوضع القديم JSON وأي أداة قديمة كاتبة يجب تعطيلهما عند الانتقال؛ قفل المحول لا يحمي من كاتب يتجاوزه.

### تسلسل الكتابة

`تحقق النطاق الموثوق قبل أي I/O → قفل → فحص الحالة → سجل النية الدائم → أثر خارجي محدود → commit corpus + audit + حالة العملية معًا → فك القفل`.

- مصادر الدفعة تُحضّر وفق القبول القائم. لكل مصدر، تثبت before/after وIDs قبل أول upsert/delete. يبقى توقيت commit النهائي للدفعة متوافقًا مع run الحالي، بما في ذلك نتائج الحجر/عدم التغير؛ لا تحويل صامت إلى commits مستقلة لكل مصدر.
- commit النهائي مشروط بالrevision الأساسي. التعارض غير المتوقع فشل آمن يتطلب reconcile، وليس overwrite.
- قبل commit: corpus القديم هو الحقيقة، لكن وجود سجلات محفوظة لا يعني أنها كانت مفهرسة. التعويض يعيد **الإسقاط النشط السابق** وفق حالة المصدر ونوع العملية:
  - run: رفع السجلات النشطة السابقة ثم حذف IDs المرشحة التي لا تنتمي للإسقاط النشط السابق، ضمن IDs المسجلة لهذه العملية فقط.
  - delete: إعادة رفع السجلات التي كانت نشطة قبل الحذف.
  - restore لمصدر tombstoned: حذف جميع IDs التي حاولت الاستعادة رفعها؛ لا ترفع سجلات before image لأنها محفوظة للتاريخ وليست إسقاطًا نشطًا. تحقق من عدم مشاركة IDs مع مصدر نشط آخر قبل أي أثر.
  - reindex: إعادة بناء النشط من corpus وعدم رفع سجلات tombstones أو النسخ التاريخية. حالة عدم وجود نشط تُعالج بتعافي حذف IDs المعروفة فقط، لا reindex فارغ ولا delete_all.
  - تثبت خطة التعويض الخاصة بالنوع في journal قبل الأثر، وتشمل حالات الفشل الجزئي وإعادة التعافي نفسه.
- هوية إعادة المحاولة: محفز المنصة الموثوق ينشئ مفتاح idempotency مرة واحدة ويحفظه في سجل الطلب المحلي قبل بدء الآثار، ويحفظ معه restore_epoch الحالي، ثم يوردهما في كل استئناف. اختلاف epoch الطلب عن المخزن المستعاد يرفض قبل أي أثر، ولا يعاد ربط المفتاح بعصر جديد تلقائيًا. يربطه المحول ذريًا بـoperation_id وdigest نية ثابت يشمل نوع العملية والمصدر والمدخلات المؤكدة وإصدار العقد. لا يولّد مفتاحًا جديدًا عند retry؛ اختلاف النية مع المفتاح نفسه مرفوض. إعادة النتيجة النهائية تسبق فحوص حالة المصدر التي تغيرت بفعل العملية السابقة. استدعاء جديد مقصود يحصل على مفتاح جديد؛ CLI الذي لا يملك مفتاح الطلب السابق لا يدعي أنه إعادة محاولة آمنة، بل يستأنف عملية محفوظة بإجراء منصة صريح. لا يُعرض المفتاح أو operation_id للعميل، ولا يُعاد استخدامه بين عبئي منصة مختلفين.
- بعد commit: corpus الجديد هو الحقيقة، حتى لو انقطع الرد للعميل. إعادة الاستدعاء بمفتاح idempotency نفسه وdigest نية مطابق تعيد النتيجة النهائية قبل فحوص دورة المصدر ودون إعادة تطبيق التغيير؛ المفتاح نفسه مع نية مختلفة مرفوض. يبقى operation_id للتتبع الداخلي فقط.
- النتائج الملتبسة تُحفظ `recovery_required`. عند فشل التعويض تبقى البوابة مغلقة؛ لا إعلان نجاح ولا حذف journal.
- مصدر تعويض IDs هو journal + النسخ المعروفة فقط؛ لا delete_all ولا حذف معرفة مشتركة غير مملوكة للعملية.
- لا ادعاء exactly-once بين SQLite والفهرس. قد تتكرر عمليات upsert/delete الآمنة على IDs محددة أثناء التعافي، ضمن سياسة المزود الحالية وموافقة التشغيل.

### الآثار المتأخرة والقراءة

إذا مات الكاتب أو انتهى timeout بعد إرسال طلب، قد يصل الأثر الخارجي لاحقًا. لذلك:

1. وجود عملية غير نهائية يغلق الكتابة الجديدة وإعادة المحاولة العادية.
2. لا تعتبر نتيجة بحث الفهرس موثوقة أثناء drift/recovery. بوابة القراءة تفحص الحالة في المحول قبل الاسترجاع وبعده، وتطابق revision وIDs/نسخة السجل مع corpus المعتمد؛ تغير الحالة خلال الطلب يؤدي إلى الامتناع.
3. لا يفتح التعافي الفهرس تلقائيًا بناء على sleep أو مرور مدة مخترعة. يلزم إثبات انتهاء/استقرار الطلب الخارجي وفق عقد المزود ثم reconcile والتحقق؛ إن تعذر الإثبات يبقى التشغيل الحي محجوبًا.
4. **دليل مطلوب قبل ربط التشغيل الحي:** تثبيت دلالات المزود الفعلية للطلب الملتبس، وحدود التحقق من استقرار الإسقاط. اختبارات المزود الوهمي تثبت كود الحالة فقط، لا هذا الضمان التشغيلي.
5. يمكن تنفيذ واختبار المحول والتعافي المعزول الآن دون التظاهر بحسم هذا الدليل. لا يغير هذا التصميم namespace العام الثابت أو يضيف generation namespace خلاف العقد الحالي.

## التدفقات والعقود الداخلية

كل التدفقات متزامنة تحت القفل، correlation داخلي operation_id، ولا يعرض للعميل. المعرفة عامة موثقة؛ journal يحفظ أقل بيانات لازمة للاسترداد؛ لا أسرار أو سياق مستأجر. الفهرس مشتق، وقاعدة البيانات مصدر الحقيقة. لا retry جديد خارج طبقة تحكم المزود؛ حدودها الحالية لا تُضاعف هنا.

| التدفق/المحفز | المنتج → المستهلك والمالك | الحد/الأثر والترتيب | التكرار والفشل | الدليل التشغيلي |
|---|---|---|---|---|
| مزامنة مأذونة | registry + Tavily → sync → corpus/Pinecone؛ عبء المنصة | فحص المصدر قبل الفهرسة؛ journal قبل upsert، corpus أخيرًا | مفتاح idempotency وdigest النية وrevision؛ قبل commit تعويض، بعده إعادة نتيجة | الحالة، عدد المصادر، الزمن، recovery_required |
| حذف/استعادة مصدر | أمر منصة → المحول → Pinecone | tombstone/restore كما العقد؛ لا حذف تاريخي شامل | إعادة التشغيل لا تضاعف التدقيق؛ تعافٍ بخطة التعويض الدائمة الخاصة بنوع العملية لإعادة الإسقاط النشط السابق | الانتقال وعدد IDs دون محتوى خام |
| إعادة بناء | corpus النشط → Pinecone | upsert النشط ثم حذف القديم المعروف؛ لا wipe | عملية journal خاصة؛ رفض corpus فارغ كما المسار الحالي، وتعافي الحذف مسار منفصل | إكمال الإسقاط مقابل فشله |
| استيراد | JSON محلي موثوق → قاعدة جديدة | تحقق شامل قبل transaction؛ لا شبكة | بصمة تمنع استيراد مكرر؛ لا overwrite | الأعداد والبصمة وصحة schema |
| نسخ/استعادة | قاعدة → نسخة مستقلة → وجهة جديدة | backup API ثم تحقق؛ تشغيل مستعاد مغلق حتى reconcile | فشل النسخ لا يمس الأصل؛ لا تبديل تلقائي | integrity + استعادة فعلية مستقلة |

العقد الداخلي المقترح: load مع revision، begin_operation، record_step، commit_expected_revision، mark_recovery_required، recover، import_verified، backup_verified. لا يُعلن API عامًا ولا تُغير عقود المال/اللقطات.

## الاستيراد والنسخ والرجوع

- الاستيراد أداة صريحة إلى قاعدة جديدة فقط، لا يحدث عند تشغيل التطبيق. يبقى JSON الأصلي دون تعديل/حذف. تحقق من schema، أنواع الحقول، source IDs الفريدة، وrecord IDs الفريدة داخل الإصدار الواحد وعبر المصادر في الإسقاط النشط، metadata المطلوبة، علاقة النسخ، tombstones، وعدم تسريب بيانات مشروع. يسمح بتكرار record ID الثابت لنفس المصدر عبر النسخ التاريخية المحتفظ بها؛ لا يعد ذلك تعارضًا ولا يُعاد توليد المعرف. تمنع مشاركة الهوية بين مصادر مختلفة في الإسقاط النشط. رفض الملف الجزئي/الفاسد بالكامل مع تقرير آمن.
- المقارنة الدلالية قبل/بعد تشمل السجلات والتدقيق والحالات والنسخ؛ لا يكفي عدد الصفوف. الاستيراد المتكرر لنفس البصمة لا يضيف نسخة أخرى؛ ملف مختلف إلى وجهة مستخدمة مرفوض.
- نسخ باستخدام SQLite backup API إلى اسم جديد ثم PRAGMA integrity_check (النتيجة ok فقط) وPRAGMA foreign_key_check (صفر مخالفات) وتحقق schema/revision وبصمة وmanifest. لا نسخ ملف قاعدة مفتوح بأداة ملفات عادية.
- الاستعادة إلى **مسار مستقل جديد** ثم تحقق وفتح قراءة فقط؛ يلزم كذلك integrity_check ناجح وforeign_key_check بلا مخالفات قبل قبول الاستعادة. اختبار مستقل يقارن corpus وjournal؛ لا يبدل قاعدة المالك.
- هوية الطلبات بعد الاستعادة: ضمان إعادة النتيجة محصور في restore_epoch نفسه. قبل فتح المخزن المستعاد للكتابة، ينشأ epoch جديد فريد بمعاملة محلية ويثبت في سجل حدث الاستعادة، مع إبقاء سجلات النسخة السابقة مؤرخة بعصرها. كل طلب صادر قبل الاستعادة يحمل epoch قديمًا فيُرفض بحالة آمنة «تغيرت نسخة المعرفة؛ راجع العملية قبل إعادة إصدارها»، حتى لو فقدت نتيجة العملية اللاحقة للنسخة. لا يدّعي النظام إرجاع نتيجة غير موجودة، ولا يستبدل epoch في retry. إصدار طلب جديد يحتاج إجراء منصة صريحًا بعد المراجعة، لا retry آليًا. اختبار إلزامي: عملية مكتملة بعد تاريخ النسخة، ثم استعادة النسخة الأقدم، ثم إعادة مفتاحها/epoch القديم؛ صفر آثار خارجية وصفر تدقيق عملية جديدة.
- عند التبديل التشغيلي المصرح لاحقًا: إيقاف الكاتبين والقراء الخارجيين، حفظ الأصل، التحقق من النسخة، reconcile الفهرس من الحقيقة المستعادة والمعرفات المعروفة في سجلات ما بعد النسخة، ثم فتحه بعد إثبات الاتساق. إن فقدت معرفة IDs اللاحقة، لا تمسح namespace للتخمين؛ تبقى البوابة مغلقة حتى إجراء استرداد مأذون.
- الرجوع للكود القديم مع JSON قديم **ليس** خطة رجوع سليمة بعد كتابات SQLite. احتفظ بالكود المتوافق والمخزن الصحيح أو نفذ تصديرًا متحققًا منفصلًا بموافقة؛ لا رجوع صامت.
- دمج القاعدة الجديدة في backup.sh وتسليم نسخة خارج volume واختبارها متطلبات لاحقة للتشغيل، لا أدلة من السكربت الحالي. RPO/RTO وحجم corpus/التحميل الفعلي غير مقاسة؛ تقاس قبل التشغيل الدوري. لا وعد إنتاجي رقمي مخترع.

## متطلبات F05-01B قبل ربط التشغيل — غير منفذة في A

محول A المدموج يقبل فقط prepared/recovery_required/committed ونتيجة committed. هذا نطاقه المعزول، وليس بروتوكول التعافي الكامل. قبل ربط run/delete/restore/reindex يجب أن تضيف B:
- إصدار مخطط جديد صريح للحالة النهائية compensated ونتيجة تشغيل آمنة محفوظة لكل عملية نهائية. compensated تعني إعادة الإسقاط السابق وعدم اعتماد after؛ لا تُسمى committed. رفع الحظر وتثبيت نتيجة التعويض الناجح يحدثان ذريًا في معاملة محلية واحدة، ولا يتمان إلا بعد تحقق الاتساق وزوال احتمال الأثر المتأخر. تعويض غير مثبت يبقى recovery_required.
- مسار توافق متحقق لمخزن A: يحافظ على corpus وrevision والـepoch وسجل العمليات والخطوات؛ لا يحول prepared أو recovery_required إلى نهائي، ولا يختلق ملخص نتيجة للعملية القديمة. اختبار المخطط الجديد في قواعد معزولة فقط، ولا ترقية تلقائية لبيانات المالك.
- هوية الطلب تحفظ قبل الآثار: key/epoch ونوع العملية والمدخل المؤكد canonical وبصمته، لا المفتاح وحده. استرجاع النتيجة النهائية يتم بالهوية والتحقق من بصمة هذا المدخل **قبل** جلب المصدر أو توليد timestamps أو after أو قراءة revision جديد لإعادة بناء النية. يحفظ السجل نتيجة آمنة كاملة؛ نفس الهوية بمدخل مختلف مرفوض.
- API begin الحالي في A يتطلب envelope كاملًا مطابقًا (kind/intent/after/expected_revision) لإعادة digest؛ لذلك لا يستعمله B كواجهة replay من مفتاح وحده. إما يحتفظ بالـenvelope المثبت نفسه دون إعادة توليده، أو يضيف lookup نهائيًا موثوقًا للمفتاح/epoch مع تحقق بصمة المدخل. يظل فحص epoch سابقًا لأي أثر، ولا يعتمد lookup على مدخل متصفح.
- الاختبارات الإلزامية: فقد الرد ثم replay بعد تغير revision/الوقت بلا أثر أو تدقيق جديد؛ تعويض ناجح يعيد نتيجة الفشل النهائية دون اعتماد after ويسمح بطلب جديد؛ تعويض فاشل/ملتبس يبقى محجوبًا؛ رفض نية مختلفة وهوية بعصر قديم قبل I/O الخارجي.
هذه متطلبات تنفيذ B وليست ادعاء وجودها في محول A، ولا تمنح تصريح شبكة أو ترحيل.

## حالة التصميم والتسليم

- F05-01A لا تغلق شرط المتانة الإنتاجية باختبار موت process فقط: يلزم إثبات إعدادات القاعدة محليًا، ويبقى دليل انقطاع المضيف/الطاقة واحترام flush مطلوبًا قبل قبول ربطها الحي. لا نجري قطع طاقة أو اختبارًا مدمرًا على خادم المالك؛ إن تعذر الحصول على دليل بيئة مماثلة يبقى هذا الشرط غير مثبت.
- `G6_NEEDS_EVIDENCE` للتشغيل المتكامل: دلالات الآثار الخارجية المتأخرة وإثبات القفل على المضيف المستهدف مطلوبان. لا يمنع ذلك بناء المحول واختباره معزولًا؛ لا يعلن `G6_DESIGN_READY` أو جاهزية نشر.
- مالك تنفيذ المحول: شريحة هندسة التخزين. تسليم الأمن: اختبارات صلاحيات الملفات والنطاق والعزل والتسريب. تسليم التشغيل: المضيف والنسخ والتراجع ودليل المزود. لا يدّعي كاتب الوثيقة اجتياز هذه الاختبارات.
- نقطة الاستئناف الحالية: F05-01B من main بعد دمج هذا التصميم؛ F05-01A مدموج في #165 وتنقيح F05-02 مدموج في #163. لا تُعاد الشريحتان. بقية بيانات الرؤوس والحالات في قسم الأدلة أعلاه توثق لحظة التصميم التاريخية.
- هذه الوثيقة لا تغلق F05-01؛ تغلق شريحة التصميم فقط بعد مراجعتها.
