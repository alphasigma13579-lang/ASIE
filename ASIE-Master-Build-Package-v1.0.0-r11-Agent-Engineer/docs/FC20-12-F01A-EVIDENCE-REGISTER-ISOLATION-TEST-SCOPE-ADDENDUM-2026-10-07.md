## 3. إضافة واحدة إلى نطاق الاختبار لاحقًا

المسار النسبي إلى جذر الحزمة:

`tests/test_tenant_isolation_matrix.py`

blob الأصل على خط الأساس: `2e093e755108fc3bb7ef4ed1b21fc42612cc5ad3`.

الإضافة المقترحة تجعل نطاق الملفات تسعة بدل ثمانية **بعد تسجيلها فقط**. الغرض المسموح:

1. إعادة استخدام Repository المؤقت، حسابات .test، مساعد HTTP وخادم loopback الموجود في fixture؛ لا بيانات مالك أو شبكة خدمات خارجية.
2. إضافة حالة جديدة لاختبار احتواء محتوى رد evidence-register لمشروع مسموح، لا استبدال اختبارات رفض مشروع/مجموعة بيانات أجنبية.
3. إبقاء كل توقعات الصلاحية والعزل القائمة وعدم تبديلها بنتيجة عامة أو skip/xfail.
4. استعمال صفوف اصطناعية صالحة ذات علامات مختلفة في A وB؛ لا مفاتيح أو بيانات حساسة.
5. تسجيل نتيجة الإثبات الفعلية على رأسه، سواء كان الفشل للعزل أو لسبب آخر. لا تُصنف مشكلة fixture أو timeout بوصفها إثباتًا لتسرب.
6. لا تعديل تجهيز تشغيل مالي قائم لمجرد تسريع الإثبات؛ fixture موجودة قد تستعمل مسار اختبار قديم، وهذا لا يمنح مسار إنتاج أو تصريح Finance جديدًا.

لا تعديل لـbackend أو src أو schema أو API أو اعتماديات أو workflow بموجب سلطة هذه الإضافة. تحتاج معالجة السبب الإنتاجي عرض نطاق مستقل، حتى لو كان ملفها أصلًا ضمن قائمة F-01A؛ إذ إن وجود المسار في القائمة ليس تصريحًا بتغيير كل سلوك فيه.

## 5. التسجيل الحاكم — الاعتمادية المطلوبة، لا فرق هذا الطلب

الترتيب وفق العقد النافذ:

1. مراجعة هذا الملحق واعتماد المالك تصميم الإضافة وغرضها على رأس محدد.
2. تثبيت checkpoint جديد لمانع اختبار احتواء الاستجابة، مرتبط بالتقرير والرأس والمصدر؛ لا إعادة استخدام checkpoint تجهيز التفسير القديم أو تغيير تاريخه/معناه.
3. تسجيل الإضافة الوحيدة واختبار حدودها مع حفظ التاريخ السابق، وموضع التنفيذ الواحد، والاعتماديات والبوابات. عند تسجيل التوقف تبقى state=IN_PROGRESS والموضع محسوبًا، وتصبح execution_authorized=false؛ يظل ذلك الحجب خلال تسجيل التوسعة، ولا ينقلب true إلا بانتقال استئناف منفصل مراجع. لا يخفي التوقف بتغيير active_target إلى null. هذه شروط انتقال مقترحة، لا وصف للسجل الحالي الذي لا يزال IN_PROGRESS/true على خط الأساس.
4. قرار استئناف جديد موضوعه checkpoint والرأس والقائمة المحققة؛ انتقال حاكم مراجع وقرار دمج منفصل قبل تعديل ملف الاختبار.
5. إثبات الاختبار على التطبيق الرسمي غير المعدل، ثم عرض إصلاح التطبيق قبل تنفيذه. إذا تطلب الخطأ توقيعًا أو ملفًا أو عقدًا آخر يتوقف الإصلاح إلى أن يعتمد نطاقه.

## 6. الإصلاح الإنتاجي — خارج هذا الملحق

الاتجاه المقترح فقط: قراءة مقيدة بمؤسسة المشروع المحفوظة خادميًا قبل التجميع، مع حماية المراجع المشتقة، fail-closed عند غياب نطاق موثوق، وإبقاء سياق HTTP الحالي.

ProjectRunDataAccess يعرّف datasets() دون وسيط المؤسسة ودون get_project؛ لذلك لا نصرح الآن بتغيير توقيع أو استدعاء مفترض. يلزم حصر المستهلكين واختيار أصغر معالجة تحفظ العقد، ثم عرض الملفات والاختبارات والمخاطر على المالك. لا API/Bus/Socket/Runtime موازٍ، ولا حل بإخفاء بيانات وصلت للعميل.

لا يُعلن VERIFIED_FIXED أو جاهزية نشر من هذا الملحق أو نجاح CI التوثيقي. لا يصح وصف risk acceptance بأنه إثبات عزل.
